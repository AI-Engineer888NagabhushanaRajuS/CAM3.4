# SPEC-026: Editable BI dashboard (Power BI / Tableau style) for Reports & Analytics and for every RFQ's OP folder

Status: proposed 2026-11-17, written in ISATVON (Harish's own format). Owner of the build: the dashboard agent. The bulk-run track (SPEC-027 notes in the handoff) calls the export script of phase 4.

## I - Instructions
Replace the fixed, hard-coded charts of the Reports & Analytics right pane, and the one-table Superset dashboard that `docker/superset/setup_dashboard.py` creates today, with a COMPLETE EDITABLE BI DASHBOARD in the style of Power BI and Tableau. A user must be able to, without a developer: add a chart, pick its visualization type and its fields (dimensions, measures, aggregations), filter and slice, cross-filter by clicking, drill, arrange and resize charts, work on several dashboard pages, save the result, and export it. No chart may be defined in React code: the chart set is DATA (Superset objects provisioned from a declarative spec file in the repo); the app only hosts it. The same dashboard, filtered to one RFQ, is delivered in each RFQ's OP folder.
Reuse an open-source BI engine instead of writing one: Apache Superset 4.1.1 (Apache-2.0) already runs here (container `cam-superset`, port 8088) and its chart builder (Explore) and dashboard edit mode are the drag-and-drop equivalents of Power BI's Fields / Visualizations panes and Tableau's shelves. Make it deep, not a skin: datasets over ALL report tables, certified metrics, native filters, cross-filtering, 4 to 6 dashboard pages, one-click edit.
Hard rules: 3.4 only (never touch MCP Jungle, Dify, Bifrost, or any container not named `cam-*`; `docker-*`, `ai-platform_*`, `mcpjungle-*`, `bullqr-*` and the rest are not ours); UI brand is "CAM 3.4" for Centum (never BuLLMQuote or SRIM); never print or log a secret (read it from the environment or the daemon `.env`, compare md5 prefixes); real proof means driving the real UI in a real browser (Playwright with the system Chrome, as in `acceptance_evidence/playwright`), not calling endpoints from a script; no canned numbers anywhere; do not remove existing features (keep the old KPI cards and charts behind a "Classic view" toggle); nothing is committed or pushed by the dashboard agent (the coordinator commits).

## A - Automation (phases; deliver a working vertical slice first, then widen)
1. DATA LAYER. New `mcp-tools/shared/analytics_publish.py` with `publish(rfq_id)`: reads the RFQ's rows from the DuckDB report tables (holding the same advisory lock the services use: `db.duckdb_file_lock()` from `fastapi-router/db.py`, for the shortest time) and writes immutable Parquet snapshots to `database/analytics/<rfq_id>/<table>.parquet` (CBOM, the 16 reports, feasibility, run inputs, plus a tidy `kpi` table with one row per metric). Run it inside the reporting container with `docker exec` (its image has duckdb and the code path; copy the file in with `docker cp` for development, the final image rebuild is done by the coordinator). Superset must read ONLY these Parquet files through DuckDB virtual datasets (`read_parquet('/app/cam-database/analytics/*/<table>.parquet', union_by_name=true, filename=true)`), never the `.duckdb` files: DuckDB does not queue cross-process access, so a Superset query could make a pipeline step fail. Add `database/analytics/` to `.gitignore`.
2. PROVISIONING FROM A SPEC. A declarative spec in `docker/superset/spec/` (YAML or JSON) lists datasets (columns, types, metrics such as total cost, priced ratio, average lead time, cash out), charts (at least 24, at least 12 visualization types: big number with trendline, bar, stacked bar, line, area, pie/donut, treemap, heatmap, scatter/bubble, histogram, box plot, funnel, sankey or sunburst, pivot table, table with conditional formatting, gauge, world-less maps are not needed) and dashboard pages (Executive overview and GO/NO-GO, Cost and price control, Lead time and feasibility and risk, Cash flow, Exceptions and data quality, All-RFQs explorer). `docker/superset/provision.py` builds the bundle or calls the REST API, is IDEMPOTENT, replaces `setup_dashboard.py` (keep the old file working), and prints the embed UUID(s). Native filters: RFQ, volume, assembly, commodity, supplier, with cross-filtering on. Every object is editable in Superset afterwards; the spec only seeds it.
3. APP INTEGRATION. The right pane (stage Reports & Analytics) shows the editable dashboard: a page selector, "View" (embedded, RFQ-scoped by default through the guest token's row-level security) and "Edit" (opens Superset's dashboard edit mode and Explore for the same dashboard, inside the pane or in a new tab, whichever works with the installed version; the local single-user setup may allow it through a documented, off-by-default config switch such as `PUBLIC_ROLE_LIKE`, never as an undocumented default). The old KPI cards and charts stay behind a "Classic view" toggle. When Superset is down or not provisioned the pane says so in one plain sentence (the existing `optionalMessage`), never a stack trace. Follow the app's design system (Tailwind, shadcn, `apps/web/src/client/components/ui`), keep new files under 200 lines, no `console.log`, run `/impeccable audit` on the changed UI before reporting.
4. PER-RFQ EXPORT (the bulk-run contract). `scripts/rfq_dashboard_export.py --rfq <rfq_id> --out <dir> [--superset-url ...]` writes into `<dir>`: `data/*.parquet` and `data/*.csv` (this RFQ's tables, loadable into Power BI or Tableau), `superset_dashboard_<rfq_id>.zip` (importable bundle), one PNG per dashboard page captured from the REAL Superset dashboard filtered to the RFQ, a full-page PDF if the installed version can, `open_dashboard.url` (an internet shortcut to the live, filtered, editable dashboard), and `dashboard_manifest.json` (what was written, sha256, the filter used, the time). It calls `publish(rfq_id)` first, exits non-zero with one clear line if Superset or the data is not reachable, never prints a secret, and is safe to run twice.
5. TESTS AND PROOF. pytest for `analytics_publish` (real DuckDB, real Parquet, hostile RFQ id like `X'; DROP TABLE x--`), for the spec validator and for provisioning idempotency; vitest for the new panel states; a Playwright run in the real UI that (a) opens an RFQ's Reports & Analytics, (b) adds a chart through the builder with chosen fields, (c) reloads and sees it persisted, (d) deletes it, (e) switches a native filter and sees numbers change; screenshots and the script saved under `acceptance_evidence/spec026/`.

## Comparison (written 2026-11-17 before the build; what each tool does that the owner means by "editable")
Power BI (Microsoft, commercial):
- Fields pane + Visualizations pane: drag a column onto a visual's wells (Axis, Values, Legend); the visual type is one click.
- Filters pane on three levels (visual, page, report) plus slicers placed on the canvas.
- Cross-highlight / cross-filter between visuals by clicking a bar; drill-down hierarchies and drill-through pages.
- Report = several pages (tabs at the bottom); bookmarks save a filter state.
- Licence and runtime: Power BI Desktop is Windows-only freeware, sharing needs Pro/Premium seats; cannot be embedded in our app without Azure capacity.
Tableau (Salesforce, commercial):
- Shelves (Columns, Rows, Marks: colour, size, label, detail) and "Show Me" to pick a chart for the chosen fields.
- Quick filters and parameters; dashboard actions (filter, highlight, URL) wire one sheet to another.
- Worksheets -> dashboards -> stories (several pages in sequence).
- Calculated fields and table calculations are written by the analyst, not a developer.
- Licence and runtime: Creator/Explorer/Viewer seats, Tableau Server or Cloud for embedding; no free self-hosted server.
Metabase (AGPL-3.0 open source, paid tiers):
- "Questions" built with a point-and-click notebook (data, filter, summarize, group by) or SQL; visual type chosen afterwards.
- Dashboards with filter widgets wired to question fields; click behaviour can filter other cards.
- Dashboard tabs (since v47) act as pages.
- Static embedding (signed JWT) is open source; interactive embedding with the builder and row-level permissions ("data sandboxing") is the paid Pro/Enterprise tier.
- No DuckDB driver in core (a community driver exists); it would be a second BI server next to the Superset that already runs here.
Apache Superset 4.1.1 (Apache-2.0, already running here as cam-superset):
- Explore = Power BI's Fields + Visualizations panes: dataset columns and saved metrics on the left, 40+ viz types, every control (dimensions, metrics, filters, sort, row limit) editable, saved as a chart.
- Dashboards: drag-and-drop grid, resize, tabs (pages), markdown, native filters (select, range, time) and cross-filtering by clicking a chart.
- Datasets with certified metrics and calculated columns; SQL Lab for analysts.
- Embedded SDK with guest tokens and row-level security per token (we use it to scope the pane to one RFQ).
- Import/export of dashboards as a YAML+ZIP bundle (our per-RFQ OP-folder deliverable) and a REST API for everything (our provisioning).
Decision: Superset stands. No blocker found; Metabase's interactive embed and row-level sandboxing are paid, Power BI and Tableau are paid and cannot be self-hosted inside the app.

## Decisions taken during the build (2026-11-17)
- Data path: Superset's database "CAM reports" (id 1, kept so `setup_dashboard.py` still works) was repointed from `reports.duckdb` to `duckdb:///:memory:`; every dataset is a virtual dataset over `read_parquet('/app/cam-database/analytics/*/<table>.parquet', union_by_name=true)`. Superset can no longer open a `.duckdb` file. The old dataset `summary_report` is redefined the same way.
- Pages: one dashboard (id 1, slug `cam-reports`, embed UUID unchanged) whose top-level tabs are the six pages. The embedded dashboard shows Superset's own tab strip as the page selector; the daemon and `App.tsx` did not need a change.
- RLS: every dataset carries `rfq_id` (the validator refuses a dataset without it), so the guest token's clause `rfq_id = '<id>'` scopes every chart. "All RFQs" in the pane mints a token without the clause.
- Edit: guest tokens cannot edit, so "Edit" opens the same dashboard in Superset itself (`/superset/dashboard/cam-reports/?edit=true`) in a new tab, signed in as a Superset user; "Open chart builder" opens Explore. No public role is created (`PUBLIC_ROLE_LIKE` stays unset).
