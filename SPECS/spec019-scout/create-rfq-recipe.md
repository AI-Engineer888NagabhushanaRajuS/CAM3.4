# Create-RFQ recipe (scout for SPEC-019 actions; read-only, no RFQ was created)

## How an RFQ is created today (intake modal path)
1. RFQ id: `projectTracking.getNextRfqId` (browser-api-server.ts ~1213) = smallest unused `RFQ-NNNNNN` over `rfq_process_tracking` UNION `rfq_project_tracking`. Pure SELECT, no sequence.
2. Customer / project master data: `customers(customer_id, customer_name)`, `projects(project_id, customer_id, project_name)`; RPCs `projectTracking.listCustomers/listProjects/createCustomer/createProject`.
3. `projectTracking.createRfq {rfqId, customerId, projectId}` (~1239): rejects when the id exists in either tracking table; checks the project belongs to the customer; `INSERT INTO rfq_project_tracking (rfq_id, customer_name, project_name, customer_id, project_id)`. That is ALL it does (no process row, no files).
4. Files: `RfqIntakeUploadModal.tsx` sends ONE multipart `POST {upload-server}/api/rfq/upload` with `bom_file`, `volume_file`, optional `gerber_file`, `rfq_id` (no `profile`), header `Authorization: Bearer <60 s JWT>` minted by `POST {bridge}/auth/token {rfq_id}` (`authFetch`, apiAuth.ts). The button needs BOTH BOM and Volume.
5. upload_server.py `upload_rfq_file`: advisory lock on the rfq_id, inserts `rfq_process_tracking(rfq_id, version, is_active, stage 0, triggered_by)` and COMMITS it, then saves each file to `staged/inbox/<rand>_<ROLE>_<name>` and inserts `rfq_file_telemetry` (file_role BOM/VOLUME/GERBER_ZIP, scan_status PENDING), then calls `trigger_dify_workflow_internal(rfq_id, False, profile)`. Returns `{success, rfq_id, version, saved_paths, telemetry.dify_pipeline_status}`. Allowed extensions: csv xls xlsx pdf zip ...
6. Pipeline start = the SAME upload request (Temporal `start_rfq_workflow`, id per RFQ, TERMINATE_EXISTING; `CAM_USE_TEMPORAL` default true). `dify_pipeline_status` is `TRIGGERED`, `ALREADY_PROCESSING` (db.try_start_pipeline_run guard), `CONNECTION_REFUSED` or `TRIGGER_FAILED`. Do NOT call `GET /api/dify/start/{id}` afterwards: that is the "continue" (resume) path and never starts a first run.

## Flow profiles
`quote_routing_profiles(profile_name, routing_sequence)`; default `CAM_DEFAULT_PROFILE` = Standard_BOM_Flow (temporal_worker/config.py); the upload form's `profile` overrides. Standard_BOM_Flow (8 centum_intake/centum_reporting tools) never writes a VOLUME row; RFQ_Flow (skills 11-16) REQUIRES a `VOLUME` row (intake__import_bom has no skip) and takes an optional GERBER_ZIP. The upload endpoint declares `volume_file` mandatory for every profile, so the chat action always needs BOM + Volume. The UI infers RFQ_Flow from the existence of a VOLUME row (no profile is stored per RFQ). The action omits `profile` exactly like the modal.

## Attachments scan API (bridge, duck_db_api.py ~1261)
- `POST /api/rfq/{id}/attachments/scan` (multipart `files`, token for that rfq id): both engines (BuLL*Sav/ClamAV + Repel Shield). Per file: `decision` released | quarantined | error, `attachment_id` = sha256[:12] only when released; quarantined/held bytes are deleted. Limits 10 files, 25 MB each, 60 MB total. ~11 s per call.
- Released files live at `staged/inbox/<rfq_id>/attachments/<sha12>-<name>` (shared `inbox` docker volume) with `audit.jsonl` (time, name, size, sha256, attachment_id, clamav, repel, decision).
- `GET /api/rfq/{id}/attachments` lists released `{attachment_id, name, size, sha256, released_at}`; `DELETE /api/rfq/{id}/attachments/{attachment_id}` removes one (audited).
- GAP: there is NO endpoint that returns a released file's bytes, and attachments are scoped to the rfq id they were scanned under (before an RFQ exists the UI must scan under some staging id). The daemon (host) cannot read the docker volume, so the file step needs a new bridge endpoint `GET /api/rfq/{id}/attachments/{attachment_id}/content` (verify_token, streams the stored file). The action then: reads bytes from the source scope, checks sha256[:12] == attachmentId, re-scans them under the NEW rfq id via the existing scan endpoint (both engines again), and uploads the same bytes to upload-server.

## Implemented step order (rfq-chat-actions.ts)
`create_rfq` (SQL equal to projectTracking.createRfq) -> `fetch_files` -> `scan_files` (both released under the new id) -> `upload_files` (POST /api/rfq/upload) -> `start_pipeline` (read from the upload response; failed unless TRIGGERED).
Rollback: failure in create/fetch/scan/upload (definitive HTTP error) deletes what this run created (rfq_project_tracking, rfq_process_tracking, rfq_file_telemetry rows for the id, attachments under the id). An upload whose outcome is unknown (network error/timeout) and a pipeline that did not start are NOT rolled back: the message says exactly what exists and that the RFQ can be continued from the UI.
Env: `PYTHON_BRIDGE_URL`/`PYTHON_SERVICE_URL` (existing), new `RFQ_UPLOAD_URL` (default http://localhost:3100; compose publishes 13100, so set `RFQ_UPLOAD_URL=http://localhost:13100` in the daemon .env). Audit: `<CAM_CHAT_AUDIT_DIR or ~/.accomplish/rfq-chat>/actions-audit.jsonl` (one JSON line: who=sessionKey, when, action, paramHash, result).
Chat staging: a file attached before any RFQ exists is scanned under the scope `chatStagingId(sessionKey)` = `CHAT-<sha256(sessionKey)[:20]>` unless the fileRef carries its own `rfqId`.
