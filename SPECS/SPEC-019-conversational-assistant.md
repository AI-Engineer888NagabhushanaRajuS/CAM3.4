## I - Instructions
Make the middle-pane assistant a NORMAL CHAT first. Plain talk ("hai how to use this tool?") gets a real, helpful answer. When the user asks about a report or any RFQ data, the assistant fetches the RFQ ids from the database and OPENS A POPUP so the user picks one or more RFQs, or presses an "All context" button. After that the user can chat about anything in that scope, and the assistant goes and fetches and dumps all the context it needs (workbook rows, RFQ state, attached files, Cognee memory). If anything conflicts or is ambiguous it says so and asks the user to choose one, or to explain. The user can upload a file in the chat and ask the assistant to use the app and create an RFQ from it; the assistant does that itself (after the user confirms). Add a strong Playwright and MCP capability for the parts of the app that only the UI can do.
Hard rules: no canned "hard-coded" replies standing in for conversation; no invented facts (every RFQ fact keeps its cell citation, every figure is verified); every write (create RFQ, upload, start pipeline) needs an explicit user confirmation showing the exact parameters; uploaded files pass both security engines first (BuLL*Sav/ClamAV + Repel Shield); 3.4 only (no Jungle, Dify, Bifrost).

## A - Automation (flows; contract the implementers share)
Scope is a UI state, not a route: `scope = { mode: 'none' | 'rfqs' | 'all', rfqIds: string[] }`. One conversation; the scope can change mid-chat and is shown as chips in the header. Selecting an RFQ in the left list sets scope to that RFQ by default.

Contract additions (daemon routing, 2026-11-05): `ChatRequest.fileRefs?: [{attachmentId, name, rfqId?}]` (scanned files attached to the turn, forwarded to `proposeCreateRfq`); `POST /api/chat/actions/confirm` also accepts the optional `params` the card showed (re-verified against the token). Multi-RFQ answers carry RFQ-prefixed citation labels (`RFQ-00001 · CBOM!A5:E5`); guide answers cite `sourceType: 'user_guide'`, label `User guide: <section>` (the `MessageCitation.sourceType` union in agent-core needs that member).
Contract additions (assistant controls the app, 2026-11-05; additive only, mirror in `apps/web/src/client/lib/chatContract.ts`): `UiDirective` += `{type:'open_rfq', rfqId}` | `{type:'open_export', rfqId}` | `{type:'open_settings', section:'providers'}`; these are BUTTONS the user presses in the bubble, the UI never navigates by itself. `confirm_action.action` is now `'create_rfq' | 'start_pipeline'` (start_pipeline params `{rfqId, stage:number|null, customer:string|null, project:string|null}`; Confirm calls GET `${RFQ_UPLOAD_URL}/api/dify/start/{rfqId}`, the call the left pane makes to resume; same single-use 5-minute token, session binding, param hash, audit lines and `steps[]` as create_rfq). `ChatActionDeps` += `proposeStartPipeline({sessionKey, rfqId})`. New deterministic intents in `rfq-chat-intent.ts` (`controlIntent`, no model): open (an RFQ id is required, nothing after it), status (pipeline words; answered from the database by `rfq-chat-status.ts`: stage n of 9, review pending, last skill rows tagged [DONE]/[RUNNING]; [FAILED] exists in the type but the database does not record failures), resume/start (refuses with a plain message when the RFQ is unknown, has no run, is finished or waits for a human review; no write), export (`open_export` only when `rfqHasExport`), upload (`ask_upload`, both engines named), settings (`open_settings` plus the line that the Local / OpenRouter / Auto switch is in the assistant header), help ("what can you do" answers from guide section 15). A figure word (total, cost, price, moq, supplier, how many ...) or a how-to phrasing keeps a message on the data / guide path; the single scoped RFQ counts as "the RFQ" when none is named.
Contract additions (SPEC-020, 2026-11-05, additive; mirrored in `chatContract.ts`): `UiDirective` += `{type:'open_manifest', path, label}` (a button-link to `#/manifests?path=<path>`); `confirm_action.action` += `'edit_value'` with params `{rfqId, bomItemId, label, field, fieldLabel, before, after}` (Confirm calls the bridge `POST /api/rfq/{id}/edit-and-regenerate`; same single-use 5-minute session-bound token, audit lines and `steps[]`: `check_row`, `edit_and_regenerate`); `ActionConfirmResponse.ui?` (`{type:'open_export', rfqId}` when the regeneration succeeded); `ChatActionDeps` += `proposeEditValue({sessionKey, rfqId, target, fieldText, value})`. New deterministic intents `edit` ("set|change|update <field or synonym> of|for <part number or bom item id> to <value> [in RFQ-x]"; the nine `final_*` fields only; refusals list the editable fields) and `manifest` ("open|show the <skill name|number|agent|reporting> manifest|skill|json", not with an RFQ id). Files: `rfq-chat-edit-fields.ts`, `-actions-edit.ts`, `-edit-deps.ts`, `-manifests.ts`.
- `{ type:'pick_rfq', reason, options: RfqSummary[], allowAll:true, allowMultiple:true }`: the UI opens the RFQ picker popup (list fetched from Postgres: id, customer, project, steps done, review pending, export available) with checkboxes, a search box and an "All context" button.
- `{ type:'disambiguate', prompt, options:[{id,label,detail}] }`: option buttons inside the bubble; clicking one sends the choice as the next user turn (or sets scope).
- `{ type:'confirm_action', action:'create_rfq', summary, params, confirmToken }`: a confirmation card with the exact parameters and Confirm / Cancel; Confirm calls `POST /api/chat/actions/confirm {confirmToken}`; the token is single-use, short-lived (5 min), bound to the session and the parameters.
- `{ type:'ask_upload', accept:[...], purpose }`: opens the file picker (then the select/reject popup and the two-engine scan that already exist).
Routing (daemon `rfq-chat-intent.ts`, deterministic rules first, model only to classify when unsure): greeting / how-to / help -> answer from the CAM user guide (a version-controlled markdown guide; the guide sections are the evidence and are cited; no RFQ facts); report or data question -> needs scope: none -> `pick_rfq`; one RFQ -> existing grounded flow; several or All -> per-RFQ evidence (top rows per RFQ plus each RFQ's Summary/Manifest/state), answered as a per-RFQ table with RFQ ids in the citations; singular question over several RFQs -> show every RFQ's answer or ask to choose; create-RFQ / upload intent -> action flow; anything else -> ordinary conversation by the model with a system prompt that forbids statements about specific RFQ data, and the verifier in "no data claims" mode.
Conflict handling: part number found in several RFQs with different values, RFQ id not found, question that names two RFQs, evidence rows that disagree, attachment contradicting the workbook: the reply states the conflict, shows both sides with citations, and asks the user to choose.
Create-RFQ action (deterministic tool, not browser automation, first): needs customer and project (ask by list if missing), BOM file (and Volume file when the profile needs it, see `RfqIntakeUploadModal.tsx`); steps after Confirm: `projectTracking.createRfq` -> scan the files with both engines under the new RFQ id -> upload through upload-server exactly as the intake modal does -> start the pipeline -> report the RFQ id and progress in the chat; every step writes an audit line (who, when, action, parameter hash, result). Failure at any step stops, says which step, and leaves nothing half-created that the user cannot see.
Playwright and MCP: run Playwright MCP (`@playwright/mcp`) as an MCP server of the agent runtime, allow-listed to the CAM web origin only, used when an operation has no API; every UI-driven write still goes through the confirmation card. First find how the agent runtime reads MCP servers (`agent-core` `generateConfig`) and whether `task-service._runTask` (the OpenCode path, currently bypassed for new tasks) must be re-enabled for this; record the finding before building.

## V - Variables
- Grounded answers: first useful text in 20 s on the local model, or streamed; the local model call must not time out silently (see handoff 2026-11-05 section 4.2).
- Scope: up to 25 RFQs in one All-context answer; above that ask the user to narrow.
- Confirmation token: single use, 5 minutes. Upload limits as the scan API: 10 files, 25 MB each, 60 MB total.
- Language of the guide and replies: English; the user may write in any style (typos, mixed words); never lecture about it.
- Tone: short, direct, no filler; show cells and sources.
