Summary

This is a working BOM/RFQ costing pipeline, not a prototype. Thirteen application services plus a Node daemon run continuously on one Windows desktop, health-checked by one script (manage_backend.py), beside a 14-container Docker Desktop stack running Dify, MCP Jungle, and Bifrost. There is no cloud deployment — a remote client reaches this machine by joining the NetBird WireGuard mesh it's already a peer of. Stop the servers here, and the client's access stops with them.

Two pipelines run end to end today: Standard_BOM_Flow through MCP Jungle, RFQ_Flow through Bifrost. A third, the FDE Staging Pipeline, has one of its six planned stages built.

The documentation and the code have drifted apart in both directions. Two security issues the docs still list as open — no auth, SQL injection — are largely fixed in code. Two subsystems that exist and run — a Cognee-backed RFQ memory service, and the FDE pipeline itself — don't appear in the docs at all. Full list under Gaps & drift.

Dify Dynamic Master Router

Two cloned apps, one node graph, one resolved mystery about a dead webhook.

Resolved, then sharpened by an independent council pass The undocumented HITL-resume webhook exists only in the daemon's own handler. Rev C traced it further: it POSTs to a URL nothing in the backend has ever listened on, and the Postgres column backing it is write-only — never read by any function in the codebase. It isn't a best-effort call that sometimes fails; it cannot ever succeed. A real, separately-built resume path works via 2 polling-based gates, not 4 as first counted.

high council Generic HITL approvals outside the 2 wired gates never resume Dify

Corrected count: exactly 2 HITL types have a working resume path — resolve_final_selection and detect_alternates (both in fastmcp-router/hitl_router.py), not 4. Any HITL decision outside those two clears the UI/DB flag but never resumes the paused Dify run — its only resume attempt targets a route that has never existed. The failure is silent: logged, never surfaced as a stuck pipeline.

high council The HITL resume webhook is dead on both ends, not just logged-and-ignored

Rev B had this half right: the webhook at browser-api-server.ts does fire. A second pass found the full mechanism: it POSTs to http://127.0.0.1:8000/api/orchestrator/resume, un-awaited, no timeout, no status check — and zero route anywhere in the Python backend receives that path. Worse: the Postgres column it exists to manage, hitl_required, is written but never read — get_hitl_state(), the only function that would read it, has zero call sites anywhere in the codebase. The real resume path works fine independently, through two correctly-wired polling gates (resolve_final_selection, detect_alternates). This webhook adds nothing but a false "success" shown to the user for an action that has zero effect — and a future engineer debugging a stuck RFQ could burn real time chasing it.

Standing rules this project operates under

Never stop a running service as routine cleanup. Services stay up continuously; a change needing a restart gets flagged and confirmed first.

Theme/styling requests stay scoped to visual tokens only — never workflow, layout structure, or business logic.
