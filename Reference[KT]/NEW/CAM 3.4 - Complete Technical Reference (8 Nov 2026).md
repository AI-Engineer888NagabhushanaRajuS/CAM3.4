### **A1. What CAM 3.4 became (the six requirements scored against the repo)**

On 5 November 2026 the 3.4 increment was defined in six requirements. Here is each one against what the repo actually holds.

1\. JSON-editable execution (ISATVON \+ Jinja2 \+ AST): PARTIALLY BUILT. The manifest editor, validation, versioning and a codegen preview exist (SPEC-020). The piece that makes a manifest actually drive a tool \- the runtime importer \- is explicitly the 4.x build chain and does not exist. The app's own banner says it: "Design input: saving versions the file; it does not yet change how a tool runs" (B, video 2:10; C, handoff 9.13).

2\. A Monaco editor in the app: BUILT. Monaco 0.57 bundled locally (no CDN), JSON-schema validation with live completion, deterministic sha256 governance hash computed on save, patch-version bump, previous copy kept in manifests/.history/, audit lines in \~/.accomplish/manifests-audit.jsonl, admin-only writes with optimistic conflict check (baseHash, HTTP 409). Repo-claimed proven live (C: save 200, v1.5.0 to 1.5.1, invalid JSON refused cleanly); the editor page is on video (B, 1:52 and 2:10).

3\. Complete dynamicness in reporting: PARTIALLY BUILT, and the two halves must never be blurred. Built: edit-and-regenerate \- the user edits one of nine allow-listed final\_\* fields in the app, the pipeline re-runs the report builder, a cell-level diff is shown, the old workbook version is kept and the new one is issued (SPEC-020; A: fastapi-router/edit\_regenerate.py read directly). Not built: SPEC-018 genuine realtime recalculation, where changing a value recalculates every dependent file and entity in realtime, including after output \- proposed only, design approval pending, engine not built (C: progress.json, TODO-3.4.md). Details in A6.

4\. UI layout: BUILT, with one honest difference from the sketch. Left pane: the workflow, now manifest-driven (SPEC-023, repo-claimed). Middle: the assistant chat pane (SPEC-006/010/016/019). Right: server-sent events, run history, live changes and output versions (SPEC-021/020). The left pane still shows the 9-stage pipeline during a run (B, video throughout); the agent \> skill \> sub-skill accordion hierarchy exists as the manifest tree on the Manifests page (B, 2:10) rather than replacing the run view.

5\. Runtime: Temporal is the orchestrator (A: CAM-Source/temporal\_worker/workflow.py is a real Temporal workflow with human-in-the-loop signals; SPEC-004/005/007/015 in the ledger). \- python-bridge (3110): the duck\_db\_api.py service the web app and daemon call for RFQ data, edits, exports and tokens. Compose publishes it as "13110:3110" on all host interfaces \- as does every other service in the file (postgres 15432, temporal 7233/8233, temporal-ui 8082, upload 13100, fastapi-router 15100, hitl 15102, MCP servers 18105/18002/18003/18007/18004); only the rfq-memory ingest listener carries a 127.0.0.1 prefix (A, full compose port list read). The SECRETS.md service map shows several internal services addressed at the LAN IP 100.121.36.255 while health endpoints stay loopback \- consistent with a single-machine dev deployment, not proof of what is reachable from elsewhere.

The editor (C, SPEC-020 \+ handoff 9.13; B, video 1:52/2:10): daemon-side routes (GET list/schema/file, PUT file), JSON Schema per manifest kind served to Monaco for live validation and completion, sha256 governance hash computed on save (replacing the old "TO\_BE\_COMPUTED\_ON\_SAVE"), patch-version bump, previous copy in manifests/.history/ (git-ignored), audit line per save, admin-only writes, stale-save protection via baseHash (409 with a Keep-mine conflict banner). The honest banner stays: saving versions the file; it does not yet change how a tool runs.

Codegen preview (C, SPEC-020 "Codegen (BAM port)"): POST /api/manifests/lint and /api/manifests/codegen, built in fastapi-router/manifest\_codegen.py with templates/skill\_tool.py.j2. Preview only: nothing is executed or written. Repo-claimed live proof: lint of all 22 manifests, 0 errors / 4 warnings (C).

What this is not: the importer that loads a certified manifest into the runtime registry, and the build-chain wiring that would make "edit the JSON and the output follows" literal. Both are the 4.x track (carried forward from the 5 November draft, Parts 1.2 and 7.6/7.8 \- still accurate as written there).

### **A6. Edit-and-regenerate vs SPEC-018 (the two halves of "dynamicness", kept separate)**

Built today (A: edit\_regenerate.py read directly; C: handoff 9.13 with live-proof numbers): POST /api/rfq/{id}/edit-and-regenerate accepts edits to the nine allow-listed final\_\* fields of the costed BOM; it applies them through the same helper as the batch-update endpoint, regenerates through the reporting MCP's export\_reports (deliberately not /tool/execute, which would advance the stage and clear the HITL gate), writes a cell-level diff across all sheets (.diff.json), reverts on failure, issues the result as a new kept version (old versions downloadable), and streams progress to the right pane over SSE. Repo-claimed live proof (C): editing final\_price\_conv 0.102 to 0.1222 on RFQ-CENTUM-PROOF-24 produced 55 changed cells across 6 sheets in 17 seconds, with the dependent total moving 1,821,701.61 to 1,821,853.11, then reverted. Allow-list, type checks, revert-on-failure and per-cell diff are all visible in the code (A). The feature was not observed in this review's 22-point video sample \- sampling cannot prove absence; code plus repo claims are its evidence today.

Not built (C, and the repo says so itself): SPEC-018, dynamic recalculation \- change a value in the app or after processing and every dependent file/entity recalculates in real time. Status in progress.json: partial; the SPEC index says "no separate file; the proposal is in TODO-3.4.md"; TODO-3.4.md says "proposed only; needs design approval before code". What exists: the golden parity harness (CAM-Source/testing/formula\_parity\_oracle.py \- LibreOffice recalculation compared against cached values) plus the ship gates, and the measured shape of the problem (27,664 formula cells, 316 distinct shapes, 57% cross-sheet in one 23-sheet export). What does not exist: the recalculation engine. This reviewer's design sketch (a proposal, not a repo claim): consume edit\_regenerate.py's per-cell diff to target only impacted formula cells, then validate against the parity oracle. Demos and docs should never let edit-and-regenerate stand in for SPEC-018 \- they are different capabilities.

### **A7. Security posture (mechanisms verified precisely)**

\- Open token mint (A): fastapi-router/duck\_db\_api.py lines 151-164 \- POST /auth/token mints a JWT for any rfq\_id or project\_id with no caller check; the code's own comment (line 1362\) acknowledges it. Tokens live 60 seconds and other endpoints verify them, but anyone who can reach the bridge can mint one. Compose publishes the bridge on all host interfaces ("13110:3110", no 127.0.0.1 prefix) \- and so does every other service in the stack; the only loopback-pinned publish in the file is the rfq-memory ingest listener (A, full compose read). A token minted for rfq\_id X also passes the rfq-memory chat listener's checks for X \- verified in source: same auth.verify\_token, same JWT\_SECRET, same claim check (A). That listener publishes on all interfaces at 18108, and each service's actual off-machine reachability is a separate unverified question. Related source finding: auth.py's verify\_token\_any\_project enforces signature and expiry but no subject match, so the FDE project create/list routes accept any token the open mint will issue (A). Verified exposure stops there: whether anything beyond that machine can actually reach the port (LAN, firewall, reverse proxy, future deployment) is unverified \- treat it as potentially reachable and fix before any shared deployment. The repo's own proposed fix: a daemon-shared secret on /auth/token, or keep 3110 off the network (C, handoff open item 1). \- Eight security decisions are queued for Harish in the repo. This review verified each mechanism in source (A) \- what the code does is established, not just asserted (C). Whether each is a defect or accepted design behavior is the owner's risk judgment: (1) the open token mint \- the risk case is this section's first bullet; (2) cross-RFQ file-reference scoping \- a client-supplied fileRefs\[\].rfqId is honored (scope \= ref.rfqId ?? stagingId in rfq-chat-actions-parse.ts) and the confirmation card shows file names only, so a crafted chat request can reference another RFQ's released file; (3) audit gaps \- only confirm.start fails closed, step-audit failures are swallowed to a log line, and audit records carry who/when/action/paramHash/result, never customer, project or file names; (4) rollback behavior \- a known HTTP failure from the upload step, including a 5xx after the pipeline may have started server-side, rolls back the RFQ rows and attachments; only an unanswered request (UnknownOutcomeError) preserves them \- the risk is deleting rows for a run that actually started; (5) RFQ-id uniqueness \- the duplicate check and the INSERT are separate statements with no transaction and no unique constraint visible in the repo (A: code search finds no DDL); the deployed database may still enforce one \- the live schema was not checked, so a race window exists in code but is unproven in deployment; (6) the confirmation-token TTL uses wall-clock Date.now \- ordinary for short-lived tokens, noted for clock-skew sensitivity; (7) the daemon listens on 0.0.0.0 (browser-api-server.ts; the file's own 127.0.0.1 header comment is stale) and chat request bodies accumulate with no size cap; (8) the planned id shown at propose time is a side-effect-free preview, naturally reused after a cancel \- design behavior, listed so the owner can confirm it is intended.

### **4.4 How the generator writes formulas (seven rules read in the SRIM code)**

> 1. One f-string per cell per row. No Excel-level fill-down: every row receives its own written string, row number substituted per data row (A{r}, H{r}).  
> 2. Row anchoring: current row \= len(rows)+1 (ex\_inv\_vl\_rows) or data\_start \+ index; the part-number key cell is always column A of the same row.  
> 3. Every lookup wrapped in IFERROR: numeric columns fall back to 0, text columns to "" (commented in \_index\_lookup). This is why tool outputs ship no \#REF\!/\#N/A in the measured set.  
> 4. Bounded ranges, not full columns: \_bounded() builds INDEX(sheet\!![][image24]C,![][image25]1):INDEX(sheet\!![][image24]C,![][image26]1\) with AL1/AK1 literal integers computed in Python; Mech & EM NRE and PCB use fixed ![][image27]282\.

## **Part I \- Formula Engine integration architecture: WORKING, 11 November 2026**

### **Status and boundary**

This is architecture preparation, not the completed stage 4 architecture or a deployment claim. Parts A-H remain the dated source record. The private Formula Engine is a separate local implementation; it is not imported by the retained CAM 3.4 edit-and-regenerate source. At 12:26 IST the independently reviewed wrapper/reference and blank/boolean repairs were integrated and the fixed MAHLE, September LAM and October LAM pack was rerun. This establishes a bounded tested local interface, not universal semantics or a completion percentage. All three outputs remain blocked for release.

### **I1. Three paths that must not be merged**

Retained CAM 3.4 source path: validate an allow-listed request \-\> read matched rows \-\> apply edits \-\> export a new workbook \-\> compare stored values \-\> attempt status events. These are source-read interfaces. Only selected validation and diff helpers have been independently executed offline here; that does not establish a production database transaction, an application run or successful rollback.  
Private Formula Engine path: load an exact XLSX \-\> represent formulas and typed values \-\> parse/evaluate selected cells \-\> record dependencies \-\> invalidate recorded dependents on an in-memory edit \-\> evaluate requested outputs with diagnostics. This is tested local code, not a replacement already connected to the application.  
Proposed application bridge: resolve an approved business edit into exact workbook/input identities, call the selected calculation path, check all output and diagnostic gates, then publish an approved new output version. This bridge is not implemented or deployment-bound by the evidence in this reference. The Parvitha repository/PPT remains mock UI context, not proof of a working bridge. CAM 3.3, retained CAM 3.4, historical SRIM and later target designs stay separate.

### **I2. Existing calculation interfaces and ownership**

Workbook(path=None, today=None, \*, decimal\_separator='.', group\_separator=',') loads workbook content. It uses separate formula and data-only reads through openpyxl. The caller can supply the calculation date and separators explicitly; a replay must record them. openpyxl is the workbook/formatting library, not the formula calculator.  
set\_formula(sheet, row, col, formula\_text) replaces a local formula and invalidates recorded dependents. set\_value(sheet, row, col, value) changes the local model and invalidates recorded dependencies. It does not write the source workbook, update a client database or discover every dependency that has never been evaluated. cell\_value\_now(sheet, row, col, budget\_seconds=None) evaluates a requested cell. Its returned value is not a whole-workbook release result. The caller must also inspect notes, cycle diagnostics and unsupported paths, including failures masked by outer formulas.  
External workbook values are typed saved-link snapshots, not live source fetches. Pivot displays remain saved snapshots: source edits can mark them dirty, but do not refresh them. The raw-cache provenance helpers are read-only audit evidence outside the evaluator/importer. They bind supported worksheet relationships, exact cell/formula identity and explicit stored empty text. They must never substitute saved results for fresh calculations.

A separate two-sheet synthetic interface check on 11 November reproduced 12 \-\> 18 \-\> 12 after edit and restore, then \#CIRC\! with an explicit cycle diagnostic for a self-reference. This confirms only that local interface sequence, not client-workbook acceptance, application integration or a full regression pass.

### **I3. Failure paths the integration must carry**

Unsupported calculation or a budget stop: return an explicit incomplete result, preserve the affected cells/diagnostics and do not turn it into a clean value. Current examples include active-filter SUBTOTAL limits and masked \_XLUDF.NUMBERVALUE diagnostics. New paths exposed by edits require another check; a prior successful sample is not a general support grant.  
Cycle or invalid reference: retain the error and its source identity. The actual MAHLE cashflow self-cycles are not repaired by choosing a plausible total. External snapshot freshness and pivot dirtiness are separate blockers even when a selected number matches a saved value.  
Unknown expected output: separate it from an engine failure and from a pass. Missing/numeric-empty caches are not certified zero; explicit stored-empty text is a historical snapshot, not independent current Excel or financial truth. Error matches remain error matches.  
Retained edit-and-regenerate failure: source code attempts a revert after apply/export failure, but a revert can itself fail. An export timeout does not cancel the worker; a late workbook may still appear. Diff failure can coexist with a completed edit/export and a ready event. A cache-status counter or zero changed-cell count is not a complete calculation or typed-propagation certificate. These behaviors need explicit states in any future adapter, not a single success flag.

### **I4. Proposed adapter contract, not an existing API**

Input identity should include the exact workbook/source hash, source variant, sheet/coordinate or business-record mapping, edit values, date/separator settings and required outputs. Business occurrence identity, volume selection and category/rounding rules require their own source-grounded decisions; a shared CPN or matching filename is not sufficient.  
The proposed result should keep fresh typed outputs, calculation errors, unsupported diagnostics, cycle/pivot/external status and expected-output evidence separate. It should identify whether a comparison used an ordinary stored value, explicit stored empty text, a saved error or no oracle. Publication should remain blocked when required output coverage or diagnostics are unresolved. No production publication or financial repair is authorized by this design note.  
Application transaction/versioning, cancellation, idempotency, UI/SSE delivery and source-ID propagation still need implementation and runtime evidence. The in-memory engine's dependency graph alone does not provide those guarantees. Formatting through openpyxl must be checked independently from calculation and against the exact output being delivered.
